Pointili developer build specification: goal, scope, Supabase data model, client and owner mobile apps, owner-controlled engagement mechanics, moment-by-moment plan, and build order.

Developer Build Spec · v1

Build Pointili — the web app.

A café loyalty + games platform. This spec is everything a developer needs to build the app (client hub, games, owner dashboard, caisse) on a Supabase backend. It excludes the marketing landing page.

Next.js + Supabase Postgres · Auth · Storage · RLS 📱 Mobile view ONLY 🎛️ Owner-controlled No landing page
00 · The goal

What we're building & why

Pointili turns one-time café customers into regulars — by rewarding them for coming back. The whole product is one loop, and it starts and ends with consuming (buying). Games and rewards are the fun in the middle that pulls people back to buy again.

The loop (memorise this — the entire app serves it) ☕ Consume → ⭐ Earn points → 🎡 Play & 🎁 Redeem → 🚶 Return → ☕ Consume…

Points are earned by buying (credited by staff at the caisse), never by playing. Playing the wheel gives prize codes; points buy real rewards. The developer's job is to make this loop fun, useful, and nice for the client — and fully configurable by the owner.

01 · Scope

What to build (and not)

✅ In scope

  • Client web app (the diner): auth, loyalty card, games, reward store.
  • Owner web app: dashboard, caisse (credit/redeem), and the full control panel.
  • Staff caisse access (PIN).
  • Supabase backend: schema, RLS, auth, storage, server-authoritative RPCs.
  • Super-admin basics (create cafés, toggle features) — optional for v1.

🚫 Out of scope

  • Marketing landing page — do not build.
  • Desktop / tablet layouts — see the mobile-only mandate below.
  • QR menu / ordering / POS — Pointili is games + loyalty only.
  • Native mobile apps — this is a web app (opened by scanning a QR).
📱 MOBILE-ONLY MANDATE — read carefully (this saves ~40% of the work) Build only the mobile view (design at 375–430px width). The client reaches the app by scanning a QR on their phone; the owner manages from their phone too. Do not build any desktop or tablet layout. On wider screens, just center the phone-width app in a max-w-[480px] column — no md: / lg: breakpoints, no responsive grids. One layout, phone-sized, everywhere.

05 · Backend

Postgres tables. Every café is a tenant (businesses); all café-scoped data carries business_id. Points are an append-only ledger — a balance is sum(delta), never a mutable column (auditable, race-safe).

06 · Security

RLS + server-authoritative RPCs

Row-Level Security (RLS) — on for every table

  • Owners read/write only rows where business_id ∈ (their businesses).
  • Public/anon may read only active/paused cafés + their public reward list (for the client hub).
  • Super-admin policy grants full access where profiles.role='super_admin'.
  • Service role bypasses RLS — used only inside trusted server routes/RPCs.

Server-authoritative RPCs (Postgres functions, security definer)

These are the only way value changes. The client calls a route → the route calls the RPC → the RPC decides & writes atomically.

-- Consume → Earn: staff credits a phone at the caisse
credit_points(business_id, phone, amount_tnd) returns balance
  -- writes +points to points_ledger (points_per_tnd × amount), grants welcome bonus once

-- Play: server picks the prize, enforces cooldown, everyone-wins
play_game(slug, phone, device) returns { prizeIndex, code, nextPlayAt }
  -- validates cooldown from plays; picks prize by config weights; writes plays + wins
  -- NEVER trust prize/odds from the client

-- Redeem: atomic spend
redeem_at_counter(business_id, phone, reward_id) returns code
  -- checks balance ≥ cost, writes −points + a redemption code, all-or-nothing

-- Engagement
touch_diner_streak(phone, xp) returns streak   -- consecutive-day count + XP
diner_wallet(phone)            returns cards    -- all cafés with activity
Non-negotiableIf the browser can set its own points or pick its own prize, the product is broken. Cooldowns, odds, balances, and redemptions are server-side only.

10 · The core

Moment-by-moment build spec

The loop has four moments. Each one has a bar to clear, the client experience, the owner controls, the backend, and a "done when". Build the app to serve these four moments.

☕

1 · Consume → Earn

at the caisse
The bar
Points land instantly and visibly, zero friction.
Client sees
A "+12 points" pop with a sound; balance grows; first-ever visit shows the welcome bonus landing.
Owner controls
points per dinar welcome bonus on/amount points expiry
Backend
credit_points() RPC via a staff caisse route; writes points_ledger; grants welcome bonus once per (café, phone).
Done when
Staff credits a phone in <5s and the diner's balance + "+points" animation update live.
🎡

2 · The Spin

the fun core
The bar
Feels like play, not gambling — and never "you lost".
Client sees
Real anticipation (slow-down + tick), an everyone-wins reveal, then a celebration (confetti + printed receipt). One free spin per visit/day.
Owner controls
wheel on/off slot on/off prizes + odds cooldown scan-to-play gate unlock gates
Backend
play_game() RPC — server picks the prize by owner weights, enforces cooldown from plays, writes wins. Odds never trusted from client.
Done when
Every spin returns a prize, respects the owner's cooldown, and can't be re-triggered by the browser.
🎁

3 · The Reward

the payoff
The bar
Rewards are desirable AND reachable (the #1 thing people get wrong).
Client sees
A ladder (cheap→aspirational), and always "just 40 pts to your free coffee". Redeem → code to show at counter.
Owner controls
reward catalogue point costs images code expiry
Backend
redeem_at_counter() RPC — checks balance, writes −points + a code atomically. Staff validates the code in the caisse.
Done when
A diner with enough points redeems, gets a code, and staff can mark it used — once.
🚶

4 · The Return

the whole point
The bar
A reason to come back that's worth the trip — without nagging.
Client sees
Streaks ("keep your 7-day streak 🔥"), "your spin is ready", weekend events, an almost-full reward they won't abandon.
Owner controls
events (double pts) streaks shown cooldown = spin cadence
Backend
touch_diner_streak() on each play; cafe_events multiplier applied in credit_points/play_game.
Done when
A returning diner sees their streak advance and any active event boost applied automatically.
11 · Make or break

The 3 things — each owner-controlled

1Instant first value

On visit #1, the diner gets welcome points + a free spin before doing anything. Never make them wait to see the point.

owner controls welcome bonus on/off + amount · whether visit-1 grants a free spin.

2Always "almost there"

Show progress to the next reward everywhere ("40 pts to a free coffee"). This goal-gradient nudge drives more returns than anything else. Computed from balance vs the cheapest reward the diner can't yet afford.

owner controls the reward ladder & prices define how near "almost there" feels — this is the tuning lever.

3Everyone wins + celebrate

No losing feeling — the wheel always gives something — and every win/milestone gets a real moment (confetti, receipt, "+points").

owner controls the prize set + odds (incl. small "consolation" prizes) so "everyone wins" stays true and affordable.

The "nice" trap — enforce simplicityThe app already has points, levels, XP, achievements, passport, leaderboard, events. Do not show all of it at once. Core loop stays dead simple — points → spin → reward. Levels/passport/leaderboard are quiet secondary layers (behind a tap), and the owner can hide them (showEngagement). Simplicity is "nice".
12 · How to do it

Build order

Phase 1
Supabase foundation. Create the project; run the schema (§05); enable RLS + policies (§06); set up Auth + the reward-images bucket; write the core RPCs.
Phase 2
Owner core. Owner signup/login, create café (unique-slug logic), dashboard shell — all mobile.
Phase 3
Diner + Ma carte. Phone+PIN auth, the loyalty card with balance + "almost there" nudge.
Phase 4
Caisse (Consume→Earn). Staff credits a phone; credit_points; welcome bonus; the "+points" moment.
Phase 5
Games (the Spin). Wheel with server play_game, everyone-wins, cooldown, anticipation + celebration.
Phase 6
Boutique (the Reward). Catalogue + redeem_at_counter + code validation in the caisse.
Phase 7
Owner control panel. Every knob from §09, grouped by moment.
Phase 8
Return layer. Streaks/daily, events, "your spin is ready", secondary meta-games (hideable).
Phase 9
Polish + mobile QA. Celebrations, empty states, error states — all at 375–430px.
13 · Definition of done

Acceptance checklist

  • A diner scans a QR, signs up with phone+PIN in ~10s, and receives the welcome bonus.
  • Staff credit points to a phone at the caisse; the diner's balance updates live with a "+points" moment.
  • The wheel always returns a prize, respects the owner's cooldown, and cannot be re-triggered from the browser.
  • A diner redeems a reward, gets a code, and staff can mark it used exactly once.
  • "Almost there" progress to the next reward shows on Ma carte and the Boutique.
  • The owner can change points rate, welcome bonus, rewards+prices, prizes+odds, cooldown, and events — and the client reflects it.
  • Streaks advance on return; an active event multiplier is applied automatically.
  • All value logic is server-side (RPC/service-role); RLS blocks cross-café reads/writes.
  • Every screen is built and tested at phone width (375–430px) only. No desktop layout exists.

That's the build.

One loop — consume, earn, play, redeem, return — made fun, useful, and nice for the diner, and fully controlled by the owner. Supabase backend, server-authoritative, mobile-only. Ship it phase by phase.
